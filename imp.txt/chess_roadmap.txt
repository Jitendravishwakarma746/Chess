Ownership tree (composition: “has-a”)

Where does everything live?
Question	Answer
Where is the board state stored?	Board.squares, a 2D list indexed [row][col]
Where are pieces stored?	Inside Square.piece. A square either holds a Piece or None
Where is movement calculated?	Board.calc_moves(piece, row, col), which fills piece.moves with Move objects
Where are legal moves (versus pseudo-legal) calculated?	The same method, with an extra filter that rejects moves leaving your own king in check (Phase 9)
Where are turns managed?	Game.next_player and Game.next_turn()
Where are chess rules implemented?	Mostly Board (movement, castling, en passant, promotion, check), with simple data on the Piece subclasses
How does rendering talk to logic?	Game.show_* methods read Board, Dragger and Config, then draw onto a surface that Main passes in. Logic never draws, and drawing never changes state
Who creates what?	Main creates Game. Game creates Board, Dragger and Config. Board creates Squares, Pieces and Moves
Two design decisions to understand before coding
A Piece doesn’t know where it is. Position is implied by which Square holds it, and Board passes (row, col) in when needed. This avoids keeping two records of the same fact (piece says “I’m at e4”, square says “I hold a piece”) that could drift apart.
Movement logic lives in Board, not in each piece subclass. The subclasses hold data (name, colour, value, pawn direction), and Board.calc_moves picks the right pattern using isinstance. This is a legitimate design, but it uses polymorphism only partly. You’ll see inheritance fully, but not the textbook “each piece computes its own moves” version. I’ll build it the tutorial’s way and explain why, and in the last phase we’ll discuss refactoring to true polymorphism (piece.get_moves(board)). That’s a good exercise, but only once you have a working baseline.

Why src/ with everything flat inside: When you run python src/main.py, Python puts the script’s own folder (src/) at the front of its import search path (sys.path). That’s why from const import * and later from game import Game work: they sit beside main.py. If game.py sat in a different folder, those imports would fail with ModuleNotFoundError. A predictable layout now saves debugging later.

Why assets/ outside src/: Images and sounds are data, not code. Keeping them apart makes the project easier to navigate and package.

Why .gitignore: Add two lines to it, __pycache__/ and .venv/. Without them, Python’s compiled cache files and your virtual environment (Step 0.3) would be committed to GitHub.

should i learn a pygame library first

No, don’t study Pygame first. There are three reasons:

Your goal is logic and OOP. The chess rules and class design train that, and they need no Pygame at all.
The Pygame you need is small. The project uses only a handful of ideas, and you’ll learn each one at the moment you need it, which sticks better than studying them up front.
Learning a library in isolation is slow and forgettable. A tutorial on drawing rectangles teaches you less than drawing your own chessboard.
